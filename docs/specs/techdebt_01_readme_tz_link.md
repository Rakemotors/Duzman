# Спека techdebt_01: README ссылка на TZ + стандарт явной привязки к версии TZ

Based on: Техническое задание v1.7 от 2026-05-19 (`docs/TZ.md`)

Issue: #8 (`tech-debt: update README link to current TZ version`)

## 1. Цель

Зафиксировать в репозитории стандарт явной привязки производных документов к
версии TZ. Источник правды — `docs/TZ.md`; производные документы, отражающие
срез TZ на момент создания, обязаны нести в шапке/тексте ссылку с указанием
версии и даты фиксации TZ.

Конкретный пользовательский эффект:
- В README указана текущая версия TZ и дата её фиксации.
- В `docs/TZ.md` появилась machine-readable шапка с версией и датой.
- Правило про привязку производных документов к версии TZ закреплено в
  `docs/TZ.md` раздел 0.4 как отдельный новый подраздел 0.4.6,
  синхронно отражено в `AGENTS.md` и
  `.claude/skills/duzman-conventions/SKILL.md`.

## 2. Контекст

В README сейчас стоит ссылка на TZ без указания версии. При bump TZ это
приводит к молчаливому рассинхрону: README указывает на live-файл, но не
фиксирует, на какой версии TZ был выпущен пакет документов на данный момент.

Принятый принцип: TZ — источник правды; производные документы, отражающие
срез TZ (README, ARCHITECTURE.md в будущем, конкретные спеки в момент
создания), обязаны явно ссылаться на версию + дату фиксации TZ. При bump
версии TZ в том же PR обновляются все живые производные документы этой
категории (смерженные ранее спеки иммутабельны — они исторические).

Документы, описывающие правила работы с TZ как с live-источником правды
(AGENTS.md, SKILL.md, AGENT_PROTOCOL.md, REVIEW_PROTOCOL.md, PR template,
самоссылки внутри TZ.md, CHANGELOG.md), привязку к версии НЕ получают —
они говорят о файле как о всегда актуальной текущей версии.

Архивные файлы `docs/archive/TZ_v*.md` иммутабельны и не трогаются.

Структура раздела 0.4 в TZ уже содержит подразделы 0.4.4 "Процедура"
(содержание PR на bump TZ — сам TZ и архивная копия) и 0.4.5 "Синхронные
апдейты конвенций" (AGENTS.md, SKILL.md, AGENT_PROTOCOL.md). Новое правило
про производные документы — это отдельная третья категория, поэтому
закрепляется как новый подраздел 0.4.6.

## 3. Зона спецификации (whitelist на запись)

Codex имеет право редактировать только следующие файлы:
- `README.md`
- `docs/TZ.md`
- `AGENTS.md`
- `.claude/skills/duzman-conventions/SKILL.md`

Любые другие файлы — read-only. В частности, ЗАПРЕЩЕНО трогать:
- `docs/archive/**`
- `docs/specs/**` (включая `day6_spec3_pattern_evaluation_engine.md`
  с устаревшей ссылкой `docs/TZ.md v1.4` — это исторический документ,
  привязанный к TZ той версии, на которой исполнялся)
- `docs/AGENT_PROTOCOL.md`
- `docs/REVIEW_PROTOCOL.md`
- `.github/**`
- `CHANGELOG.md`
- любой код в `src/`, `tests/`, `alembic/`

### 4.1 docs/TZ.md

Шаг 1. После строки `Версия 1.7 · 19 мая 2026` (строка 3) вставить пустую

Шаг 2. Добавить новый подраздел 0.4.6 "Синхронные апдейты производных

"Синхронные апдейты конвенций". Подраздел 0.4.5 заканчивается строкой про

ПОСЛЕ последнего пункта 0.4.5 и ПЕРЕД следующим существующим заголовком
(подразделом 0.4.7, разделом 0.5 или иным, что идёт сразу за 0.4.5).

Содержание нового подраздела 0.4.6:

    0.4.6. Синхронные апдейты производных документов

    Если в репозитории присутствуют производные документы, отражающие срез
    TZ на момент их создания и несущие в шапке или тексте явную привязку к
    версии и дате фиксации TZ формата
    `Техническое задание vX.Y от YYYY-MM-DD` или
    `Based on: Техническое задание vX.Y от YYYY-MM-DD`,
    то в PR на bump версии TZ они обновляются на новую версию и новую
    дату фиксации.

    К этой категории относятся:
    - README.md
    - ARCHITECTURE.md (когда появится)
    - другие живые производные документы того же класса

    К этой категории НЕ относятся (привязку к версии не несут, при bump
    не обновляются):
    - AGENTS.md, .claude/skills/duzman-conventions/SKILL.md,
      docs/AGENT_PROTOCOL.md, docs/REVIEW_PROTOCOL.md — это конвенции,
      они обновляются по правилам 0.4.5 при изменениях процессного характера,
      а не при каждом bump TZ
    - .github/pull_request_template.md, CHANGELOG.md, самоссылки внутри
      docs/TZ.md — они говорят о TZ как о live-документе
    - docs/archive/TZ_v*.md — иммутабельные снапшоты прошлых версий
    - docs/specs/* — исторические документы, привязанные к версии TZ
      того момента, когда спека исполнялась; после мержа PR по спеке она
      не обновляется

### 4.3 AGENTS.md

Добавить новый раздел про стандарт ссылок на TZ. Место — после
существующего вводного блока про TZ как источник правды (вокруг строк
7-11), перед следующим разделом.

Содержание раздела:

    ## Ссылки на TZ из других документов

    Различаем две категории упоминаний TZ:

    Категория 1: live-ссылка (без версии).
    Документ описывает TZ как всегда актуальную текущую версию.
    Формат: `docs/TZ.md` или `[docs/TZ.md](docs/TZ.md)`, без явной версии.
    Применяется в: AGENTS.md, .claude/skills/duzman-conventions/SKILL.md,
    docs/AGENT_PROTOCOL.md, docs/REVIEW_PROTOCOL.md, .github/pull_request_template.md,
    CHANGELOG.md, самоссылки внутри docs/TZ.md.

    Категория 2: версионная ссылка (с версией и датой фиксации).
    Документ отражает срез TZ на момент создания/обновления.
    Формат текста в документе:
    `Техническое задание vX.Y от YYYY-MM-DD ([docs/TZ.md](docs/TZ.md))`
    или в шапке производного документа:
    `Based on: Техническое задание vX.Y от YYYY-MM-DD (docs/TZ.md)`
    Применяется в: README.md, ARCHITECTURE.md (когда появится), и любых
    будущих производных документах, несущих срез TZ.

    При bump версии TZ через PR (см. docs/TZ.md раздел 0.4, подраздел 0.4.6)
    все живые документы категории 2 обновляются в том же PR на новую
    версию и новую дату фиксации. Документы категории 1 при bump TZ
    по этому правилу не обновляются.

    Архивные файлы docs/archive/TZ_v*.md иммутабельны.

    Спеки в docs/specs/* являются историческими документами и сохраняют
    ссылку на ту версию TZ, на которой исполнялись. При bump TZ ранее
    смерженные спеки не обновляются.

## 7. Workflow по Issue #8

1. Создать ветку от main: git checkout -b techdebt/08-readme-tz-link
2. Внести изменения по разделу 4.
3. Прогнать команды проверки из раздела 6.
4. Закоммитить с сообщением, ссылающимся на Issue #8.
5. Запушить ветку, открыть PR с шаблоном .github/pull_request_template.md, указать Closes #8.
6. В отчёте Operator-у приложить:
   - ссылку на PR
   - вывод всех команд из раздела 6
   - подтверждение, что файлы вне whitelist не изменены (вывод git diff --stat)
