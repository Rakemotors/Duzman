# Spec: agents_md_docs_practice

## Контекст
Текущий AGENTS.md содержит минимальные требования по docstrings.
В процессе работы над Спеками 1-3 выявлено: Codex пишет docstrings
одной строкой, без описания параметров и возвращаемых значений, без
header-комментариев модуля и без inline-комментариев в сложных местах.
Этого недостаточно для долгосрочной поддержки кода Operator-ом, который
не является программистом.

Задача: уточнить раздел 3 AGENTS.md и синхронизировать копию в
.claude/skills/duzman-conventions/SKILL.md. Минимально и достаточно.

## Цель
Раздел 3 AGENTS.md содержит явные требования к четырём уровням
документации в коде:
1. Header-комментарий каждого .py файла (назначение модуля, его роль
   в архитектуре, ключевые публичные сущности).
2. Module-level docstring сразу после header-комментария.
3. Docstring каждого класса и каждой публичной функции/метода: краткое
   описание (одна строка), при необходимости расширенное описание,
   список параметров с типами и смыслом, описание возвращаемого
   значения, описание исключений если функция их бросает.
4. Inline-комментарии в сложных или неочевидных местах: объяснение
   "почему так", а не "что делает код".

## Выходы

Изменение AGENTS.md, раздел 3 "Конвенции кода", подраздел "Docstrings"
переименовать в "Документация в коде" и переписать так:

    ### Документация в коде

    Документация пишется на четырёх уровнях. Все уровни обязательны.

    1. Header-комментарий файла. В начале каждого .py файла короткий
       комментарий из 1-3 строк: для чего этот модуль, его роль в
       архитектуре проекта, какие ключевые публичные сущности он
       экспортирует. Пример:
       # src/duzman/patterns/snapshot.py
       # Pattern Engine — Snapshot Layer. Собирает значения метрик из БД
       # в immutable MetricsSnapshot для evaluation.

    2. Module-level docstring сразу после header-комментария.
       Одна строка с кратким описанием модуля.

    3. Docstring каждого класса и каждой публичной функции/метода:
       - Краткое описание одной строкой (что делает, не как)
       - При нетривиальной логике — расширенное описание после пустой строки
       - Параметры: имя, тип через type hints в сигнатуре, краткий
         смысл в docstring если он не очевиден из имени
       - Возвращаемое значение: что возвращает, в каких случаях None
         или специальные значения
       - Исключения: что бросается и в каких условиях, если функция
         бросает исключения как часть контракта

       Private функции с префиксом _ — docstring одной строкой,
       параметры можно не описывать если они очевидны.

       Типы — через type hints в сигнатуре, не в тексте docstring.

    4. Inline-комментарии в сложных местах. Объясняют "почему", а не
       "что". Если код требует комментария на каждой строке — это
       признак что код надо упростить, а не закомментировать. Магические
       числа и неочевидные значения должны быть либо вынесены в
       именованные константы, либо прокомментированы.

    Язык: всё на английском (код, комментарии, docstrings, commit
    messages, ARCHITECTURE.md, CHANGELOG.md, README.md).

После этого раздел 6 "Документация" остаётся как есть (он про
проектную документацию ARCHITECTURE.md/CHANGELOG.md/README.md, не
про документацию в коде).

правка того же раздела.
