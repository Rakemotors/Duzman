# Регламент работы AI-агентов в проекте Duzman

Дополнение к Приложению Е ТЗ v1.3. Описывает практический протокол передачи задач между Operator, Claude (web), Claude Code и Codex CLI.

## Роли

- Claude (web, claude.ai) — архитектор. Пишет спецификации по Приложению Г ТЗ, делает code review, ведёт изменения ТЗ. Кода в репо не пишет.
- Codex CLI — исполнитель на VPS. Работает в ~/duzman под пользователем ubuntu. Push запрещён.
- Claude Code — второй исполнитель на VPS. Работает в ~/duzman под пользователем ubuntu. Push запрещён.
- Operator — координатор. Передаёт спецификации, контролирует переходы, делает git push вручную.

## Жизненный цикл одной задачи

1. Claude (web) выдаёт Operator-у спецификацию по формату Приложения Г ТЗ.
2. Operator копирует в исполнителя (Codex или Claude Code) стартовое сообщение со встроенной спецификацией.
3. Исполнитель выполняет задачу, в конце выдаёт отчёт по фиксированному формату.
4. Operator пересылает отчёт Claude (web) для ревью.
5. Claude (web) либо одобряет, либо просит правки.
6. После одобрения Operator делает git push origin main в терминале VPS.
7. Переход к следующей задаче.

## Стартовое сообщение для исполнителя

Operator вставляет в сессию Codex или Claude Code сообщение по следующему шаблону. Плейсхолдер в конце заменяется реальной спецификацией перед отправкой.

---

Прочитай docs/TZ.md (актуальная версия ТЗ, источник правды).
Прочитай ARCHITECTURE.md (текущее состояние архитектуры).
Прочитай AGENTS.md (конвенции проекта, если ты Codex) или .claude/skills/duzman-conventions/SKILL.md (если ты Claude Code).

Затем выполни спецификацию ниже строго по формату Приложения Г ТЗ.

В процессе работы:
- Пиши docstrings на всех новых публичных функциях, классах, методах
- В сложных местах добавляй короткий поясняющий комментарий (зачем, не что)
- После завершения прогони локальные тесты: .venv/bin/pytest -q
- Если тесты красные — не считай задачу выполненной

В конце задачи выдай отчёт в следующем формате:
1. Что сделано (1-3 строки)
2. Изменённые файлы (список)
3. Вывод команды git diff --stat
4. Вывод команды .venv/bin/pytest -q (последние 20 строк)
5. Вывод чек-листа критериев готовности из спецификации (каждый пункт: PASS/FAIL + короткий комментарий)
6. Хеш коммита (git log -1 --oneline)
7. Обновлён ли ARCHITECTURE.md (да/нет, какая строка добавлена)

Запрещено:
- git push
- sudo, apt, systemctl, service
- чтение или модификация .env, ~/.ssh, /etc/, /opt/duzman
- запуск live API вызовов в тестах
- изменения вне зоны, описанной в спецификации

Спецификация:
[здесь Operator вставляет полную спецификацию задачи]

## Жёсткие правила для исполнителя

- Каждая новая публичная функция/класс/метод имеет docstring.
- Сложная логика снабжается коротким комментарием с обоснованием.
- В конце каждой задачи запускается полный .venv/bin/pytest -q. Зелёные тесты — обязательное условие приёма.
- В конце задачи обновляется ARCHITECTURE.md (одна-две строки).
- Один коммит на задачу, осмысленный commit message.
- Push делает Operator, не исполнитель.

## Что считается провалом задачи

- Любой FAIL в чек-листе критериев готовности.
- Красные тесты.
- Изменения в файлах вне зоны спецификации.
- Отсутствие docstrings на новых публичных API.
- Отсутствие обновления ARCHITECTURE.md.
- Исполнитель замолчал в середине задачи (исчерпал ресурс).

При провале задача передаётся другому исполнителю с пометкой о состоянии.

## Действия Operator после отчёта исполнителя

1. Скопировать отчёт исполнителя в чат с Claude (web).
2. Дождаться ревью от Claude (web).
3. Если ревью положительное — выполнить в терминале VPS: git push origin main
4. Если Claude (web) нашёл проблему — вернуть исполнителю уточнённую задачу.

## Стратегия загрузки агентов

Codex и Claude Code имеют независимые лимиты по времени и токенам. Claude (web) и Claude Code расходуют общий пул Pro-подписки Anthropic. Поэтому порядок работы:

1. Сначала максимально загружается Codex (его лимит независим).
2. Когда Codex исчерпан или замолчал — переключение на Claude Code.
3. Когда Claude Code исчерпан — пауза до восстановления квот.

Claude (web) активно используется на первой фазе как бесплатный для общего пула ресурс — для подготовки спецификаций и ревью.
